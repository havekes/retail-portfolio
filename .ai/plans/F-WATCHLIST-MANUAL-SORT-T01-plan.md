## Objective

Give watchlists a persisted sort mode, and give each watchlist membership a persisted date-added timestamp and manual position, so custom (manually reordered) ordering survives reloads instead of living only in user preferences.

## Scope

**In scope:**
- `src/market/model.py`: add a non-null `sort` column to `WatchlistModel` (server default `custom`) and non-null `added_at` / `position` columns to `WatchlistsSecuritiesModel`.
- Alembic migration adding the three columns, backfilling existing rows, then enforcing NOT NULL.
- `src/market/repository_sqlalchemy.py`: make the add-security paths write `added_at = now()` and `position = (max position in that watchlist) + 1` for every new membership.
- Update test fixtures and direct model construction that create membership rows.

**Out of scope:**
- Exposing the new fields through the read API (F-WATCHLIST-MANUAL-SORT-T02).
- Sort update and reorder endpoints (F-WATCHLIST-MANUAL-SORT-T03).
- Frontend changes.

## Acceptance criteria

- [ ] `market_watchlists` has a NOT NULL `sort` column defaulting to `custom`.
- [ ] `market_watchlists_securities` has NOT NULL `added_at` (timezone-aware) and `position` (integer) columns.
- [ ] The migration backfills existing watchlists with `sort = custom` and existing membership rows with a deterministic per-watchlist `position` and a non-null `added_at`; downgrade drops the columns cleanly.
- [ ] Adding a security to a watchlist stores a non-null `added_at` and a `position` greater than every existing position in that watchlist.
- [ ] Re-adding a previously removed security gives it a fresh position at the end.
- [ ] `tests/test_migrations_autogenerate.py` passes (no ORM/migration drift).
- [ ] Build passes and relevant tests pass.

## Technical notes

- Migration must use the standard autogenerated revision flow; add columns nullable, backfill with `op.execute`, then `alter_column(..., nullable=False)`.
- `added_at` can use a database server default of `now()`; `position` is application-managed, so every code path that inserts a membership must set it (the `secondary` relationship append must not bypass this).
- Existing membership rows carry no ordering information; choose a deterministic backfill order per watchlist and document it in the migration docstring.
- Direct membership construction exists in `tests/repositories/test_repository_sqlalchemy.py` (delete-cascade test) and must be updated.
- Fixtures in `tests/fixtures/market.py` construct `WatchlistModel` without `sort`; rely on the default or set it explicitly.

## Plan

**Approach:** Add the three columns to the ORM models and generate the standard Alembic migration with the nullable → backfill (`op.execute`) → NOT NULL pattern. Because the `WatchlistModel.securities` `secondary` relationship cannot write extra association columns (it issues a bare `INSERT INTO market_watchlists_securities (watchlist_id, security_id)`), the add-security path in `SqlAlchemyWatchlistRepository` is changed from a relationship append to an explicit `WatchlistsSecuritiesModel` insert with `added_at=now()` and `position = max(position)+1` computed via a scalar subquery; reads and removals keep using the existing relationship. Rejected alternative: an association-object model (`Association` class on the relationship) — larger refactor of the `WatchlistRead` mapping for no benefit in this ticket, since no API changes are in scope.

**Risks / watch-outs:**
- The `secondary` relationship (`WatchlistModel.securities`) becomes read/delete-only: never both explicitly insert a membership row and append to the loaded collection in the same session, or you get an IntegrityError from the redundant INSERT. Removal via `collection.remove(...)` is safe (delete-only).
- `added_at` tz-awareness: Postgres `timestamptz` via `DateTime(timezone=True)`; in tests compare only with tz-aware `datetime.now(UTC)` values.
- Autogenerate drift: the new migration's `server_default` values and nullable sequencing must mirror the ORM exactly (`"custom"` on `sort`, `now()` on `added_at`); `position` gets no server default (application-managed) in either.
- Position max is computed at insert time (`coalesce(max,0)+1` in the same INSERT); not concurrency-safe under simultaneous adds — acceptable for single-user watchlists; note it in the repository docstring rather than adding locking (out of scope).
- Backfill determinism: existing membership rows have no natural order; `ORDER BY security_id` is arbitrary but stable and must be documented in the migration docstring (ticket requirement).
- Migration head: if `feat/f-watchlist-manual-sort` has gained other revisions, re-check `alembic heads` before generating — a merge revision may be needed.
